# AI usage

This project was built with Claude Code as a pair programmer. This file
describes how I used it: what it generated, what I decided, which prompts
and approaches worked, what had to be corrected, and where I chose
differently from what it suggested.

## 1. How I worked

I did not ask for code and accept what came back. Every feature went
through the same loop:

1. I state what is needed and the constraints I care about.
2. We discuss the options and their trade-offs; I decide.
3. The assistant writes a plan: files, flow, risks, how it will be tested.
4. Nothing is written until I approve the plan. Scope cannot grow without
   coming back to me.
5. The assistant generates the code and the tests.
6. I review the code, ask questions, and request changes.
7. The feature is run for real, not only under test.
8. It is committed only then, and only when I ask.

The loop is not a habit, it is enforced. I keep a standing instruction
file (`CLAUDE.md`) that Claude Code loads into every session. Two of its
rules, quoted as written:

> Before making ANY code change, you MUST first analyze the request and
> existing codebase, present a clear implementation plan, and wait for
> explicit user approval.

> Passing tests MUST NOT be treated as proof that an implementation is
> correct or production-safe. Tests are evidence, not proof.

This file was the single most effective prompt of the project: it turned
every request into a design conversation first and a diff second.

### The loop on a real feature: email verification and password reset

Neither is in the task description. I added both because sign-up without
them is not something I would call production-ready.

- **What I asked for.** Verify the address before the first sign-in, and
  let a user recover a forgotten password. The assistant pointed out that
  this was beyond the brief; I kept it.
- **What I decided in the discussion.** A 6-digit code instead of a link.
  A 5-minute lifetime. Sign-in refused for an unverified address, but only
  after the password is correct. Rate limits on every auth endpoint. No
  automatic deletion of unverified accounts.
- **The plan.** Hashed codes bound to the user and the purpose, a limited
  number of attempts, one live code per user, a one-minute resend
  cooldown. I approved it, then asked for the session part to be
  hand-written rather than built on a very new library.
- **What I changed after reading the generated code.**
  - Sign-up answered the same way whether or not the address existed. I
    changed it to say plainly that the email is already registered: the
    uniform answer protected little here and confused real users.
  - The "send the code by email" block existed twice, once for
    verification and once for reset. The assistant proposed leaving it,
    to avoid touching passing tests. I asked for one function.
  - I asked for step-by-step debug logs, and for interfaces to live in
    their own files.
- **How it was verified.** Unit and end-to-end tests, then by hand against
  the running containers, then with real email: both the verification and
  the reset message were sent through the provider and arrived in my
  inbox before the code was committed.

## 3. Prompts and approaches that worked

**Strategy before any code.** My first message on the back end was "let's
start with a strategic discussion first", and I asked whether the choice
of authentication strategy would affect deployment. The session model
(short access token, rotating refresh token, HttpOnly cookies) was settled
in that conversation, so no code was written against a design that changed
later.

**"Show me the official example."** When the assistant proposed its own
folder layout for database schemas, I asked for the example from the
NestJS documentation and chose that instead. Asking for the primary source
also exposed claims the assistant had made from memory that were wrong for
the current version.

**Requirements up front.** Before any front-end code I gave four things it
had to respect: feature-based folders, route-level code splitting, request
cancellation, and explicit HTTP error handling. Stating constraints first
was far cheaper than correcting the output afterwards.

**A throwaway prototype for design.** The look was iterated in a single
HTML file, with screenshots going back and forth, until I was happy. Only
then was it built in React. Many ideas were tried and dropped without
touching the real code.

**"I will review first."** After each phase I read the code before
allowing a commit. Before the first commit I asked for a full pass: remove
comments that add nothing, add logs where they are missing, report
anything wrong. That pass found a real start-up bug.

**"Prove it outside the tests."** Green tests were not where I stopped. I
asked for every kind of email to be sent for real before committing, and
for the screens to be checked at phone size, in real Chrome, and for
keyboard and screen-reader use. Each of those checks found something the
tests had not.

## 4. What had to be corrected or reworked

The assistant was fast and usually right. These are the places where it
was not, grouped by what caught the problem.

### Caught by my review

- **The same block written twice.** Sending a code by email existed once
  for verification and once for password reset. The assistant suggested
  leaving it, to avoid touching passing tests. I asked for one function;
  it became a small service with one entry per kind of code.
- **Logs that could not answer "why".** A failed email logged only an
  error class. After my request for step-by-step logs it reports the
  provider's status and whether a retry can help, still without any
  address, code or token.
- **A blank setting stopped the API from starting.** Found in the full
  review pass before the first commit: an empty mail key in the
  environment file crashed start-up even when no email was being sent.
- **A second review after the first submission.** It found four things the
  first pass had let through: the verify-email form was built differently
  from the reset-password form although both collect the same code; a
  shared hook sat in the UI components folder; the front end ran only the
  template's default lint rules; and many comments restated the code. All
  four were fixed in one reviewed pull request.

### Caught by running it for real

- **A backdrop that never showed.** The page's own background painted
  over the gradient behind it. No test failed; it was visible only in a
  screenshot of the running container.
- **Phone and accessibility gaps.** Checking at phone size and with the
  keyboard found inputs that would make iOS zoom the page, a title that
  could break in the middle of a word, every page sharing one browser
  title, and a route change that announced nothing to a screen reader.
- **A promise the code did not keep.** The README said that when two tabs
  renew the session at once, the losing tab simply retries. The first
  version of the client gave up instead. Fixed, with a test for it.

### Caught by tests and CI

- **Wrong from memory.** The assistant assumed an older NestJS and first
  said Zod validation would need a third-party bridge. The scaffolded
  project was a newer major version with first-party support, and the
  plan was revised before any feature code was written. Later it reported
  a router version that was not the one installed.
- **The first CI run failed, and so did the first fix.** The database
  container refused to start on GitHub's runners because of a kernel
  incompatibility in MongoDB 8. The assistant guessed the runner image
  was the cause and pushed a pin that changed nothing. Reading the
  container's own log gave the real cause; Compose and CI moved to
  MongoDB 7, because the same failure would have hit anyone running the
  project on a recent Linux host.

## 5. Where I decided differently

| The assistant suggested                                                                  | I decided                                        | Why                                                                                                                                                                |
| ---------------------------------------------------------------------------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Keep to the brief: sign-up, sign-in, one protected page                                  | Add email verification and password reset        | An account system without them is not production-ready, which is what the task asks for                                                                            |
| A verification link sent by email                                                        | A 6-digit code typed into the app                | It is the pattern users already know from most large products, and it keeps them in the same tab instead of sending them to their inbox and back on another device |
| Answer sign-up the same way whether or not the address exists                            | Say plainly that the email is already registered | The uniform answer hid little and left real users waiting for an email that never came; resend and reset stay uniform                                              |
| Build sessions on the new official authentication package                                | A small hand-written implementation              | The package was pre-1.0. For something as sensitive as sessions I preferred the established approach until that release is fully proven                            |
| Email the user when their password changes, and delete unverified accounts after a while | Neither                                          | Both add moving parts (another mail, a background job) for little gain here                                                                                        |
| Its own folder layout for the database schemas                                           | The layout from the NestJS documentation         | A reviewer who knows NestJS should find things where the docs put them                                                                                             |
| Design directions with lamps, textures and coloured walls                                | A plain card on a flat black wall                | After trying them all in the prototype, the quietest one looked the most professional                                                                              |

It went both ways. I first asked for class-validator; the assistant showed
that the installed NestJS version supports Zod schemas natively, with one
schema driving validation, types and the API documentation, and I
switched.

## 6. Scope and time

The brief asks for sign-up, sign-in and one protected page. I went further
on purpose.

**What the brief asks for:** the three pages, the field rules, a NestJS and
MongoDB API with a protected endpoint, a README.

**What I added:** email verification, password reset, rotating refresh
sessions, rate limiting, structured logging, a uniform error format,
Swagger, unit and end-to-end tests, CI, Docker Compose for the whole
stack, a custom design, and a live deployment.

**Time.** About six hours of work in total, spread over one day. The
required scope was the smaller part of that. The rest went to the
additions above, to the design, and to the problems that came up along
the way.
